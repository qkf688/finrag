# FinRAG

金融知识库 RAG 检索层与评测 —— 独立项目，目标是把「LLM + 检索」做出**可复现、可量化**的证据。

对应 JD 要求（`AI 全栈开发工程师`）：req-005 搭建与优化金融 RAG 知识库与检索增强生成系统（must_have）。

## 为什么做这个

- 这类岗位的 JD 写的是「搭建和优化」，落点就是**评测数字**：检索召回率、答案忠实度、延迟。没有数字就只是堆功能。
- 独立仓库叙事更清楚：不挂在别的项目下面，README 一眼能看懂「做了什么、怎么测的、结果如何」。
- 全流程离线可复现：默认用哈希基线做检索评测，模型可替换；没有 GPU、没有 API key 也能把评测表跑出来。

## 架构

```
corpus/*.md ──split.py──> chunk(doc_id, section, text)
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        BM25（纯 Python）              embed.py（Hash / 本地模型）
              │                               │
              └────── retrieve.hybrid_search ──┘   RRF 融合 → top-k
                              │
                     answer.py 组装带引用的答案 / 拒答
                              │
                     evaluate.py 出评测表
```

- `src/finrag/split.py`：按标题 + 段落切分，带 overlap。
- `src/finrag/embed.py`：中文按「单字 + 二元组」分词；`HashEmbedding` 是确定性离线基线，`LocalEmbedding` 用本地 bge-small-zh。
- `src/finrag/retrieve.py`：BM25 + 向量索引 + RRF 混合召回。
- `src/finrag/answer.py`：提示词要求「只依据片段回答」，输出 JSON（答案 + 引用）；得分低于阈值直接拒答。
- `src/finrag/evaluate.py`：Recall@K / MRR@K / 引用支撑度 / P50、P95 延迟。

## 复现实验

在仓库根目录设置 `PYTHONPATH=src`（Windows PowerShell：`$env:PYTHONPATH="src"`）：

```bash
python -m ruff check src tests
python -m pytest -q
python -m finrag.cli report --backend hash --out results/report-hash.md
python -m finrag.cli report --backend local --out results/report-local.md
```

`report` 会重新生成上面的表；`local` 需要本机可用的 sentence-transformers 与 bge-small-zh。

## 快速开始

# Windows
.\scripts\setup.ps1

## 评测表

### 真实语料（东方财富公开财经新闻，2026-11-23 抓取）

- `scripts/fetch_eastmoney_corpus.py`：列表页 → 36 篇正文（保留原文 URL 与抓取日期）；
- `scripts/make_real_eval.py`：从真实正文自动构造 120 条问答，标注到**文档级**（因为自动生成只能保证答案在该文档里）；
- 评测口径：召回命中「同一 doc_id 的任意 chunk」；实体门禁识别不出主体名时跳过。

`python -m finrag.cli report` 实测（k=5，数值来自 `results/report-hash.md` 与 `results/report-local.md`）：

**HashEmbedding 512 维离线基线**

| 方案 | Recall@5 | MRR@10 | P50 (ms) | P95 (ms) |
|---|---:|---:|---:|---:|
| BM25 | 0.775 | 0.666 | 6.655 | 7.607 |
| 纯向量 | 0.550 | 0.407 | 16.524 | 97.895 |
| 混合召回（RRF） | 0.592 | 0.503 | 131.741 | 188.988 |
| 混合 + 重排 | 0.592 | 0.519 | 139.208 | 192.468 |

**本地 bge-small-zh（query 侧加中文指令前缀）**

| 方案 | Recall@5 | MRR@10 | P50 (ms) | P95 (ms) |
|---|---:|---:|---:|---:|
| BM25 | 0.775 | 0.666 | 38.412 | 47.975 |
| 纯向量 | 0.425 | 0.330 | 157.164 | 208.732 |
| 混合召回（RRF） | 0.517 | 0.431 | 192.018 | 235.518 |
| 混合 + 重排 | 0.508 | 0.429 | 196.957 | 239.081 |

结论（真实语料，不再全是 1.0）：

- **BM25 最强（0.775 / 0.666）**；HashEmbedding 纯向量次之（0.550 / 0.407），本地 bge-small-zh 只有 0.425 / 0.330，低于哈希基线与 BM25，属于负结果，没有继续硬调。
- **混合召回没有超过 BM25**（Hash 0.592 / Local 0.517），RRF 把 BM25 排第一的相关文档稀释了；在「查询词几乎都来自原文」的自动问答上，词面匹配本就是强信号。
- **重排只在 Hash 上略正**（0.503 → 0.519），在 Local 上反而略负（0.431 → 0.429）——同一改动在不同 embedding 上结论不同，保留完整对照。
- **延迟**：BM25 在 Hash 下 P50 6.7ms、Local 下 38.4ms；混合路径主要成本是纯 Python 对 345 个 chunk 打分，上规模后要换倒排索引。

### 合成语料（早期基线，对照用）

40 篇合成金融文档 + 80 条问答，每个 section 都带唯一公司名：

| 方案 | Recall@5 | MRR@10 |
|---|---:|---:|
| BM25 | 1.000 | 0.721 |
| 纯向量 | 1.000 | 0.760 |
| 混合召回（RRF） | 1.000 | 0.727 |
| 混合 + 重排 | 1.000 | 0.688 |

合成基准太易，Recall 全 1.0；重排在合成集上是负结果（0.727 → 0.688），在真实集上略正（0.503 → 0.519）——同一改动在不同数据上结论相反，这正是要做多组对照的原因。

## 拒答与引用（实体门禁）

金融问答里「同名指标不同公司」靠分数阈值挡不住：问「星海量子 2024 年营业收入」，语料里每家公司都有「2024 年营业收入」这句话，BM25 分数照样很高。所以加了一层实体门禁：从问句开头抽出主体名（`星海量子`），必须出现在引用片段里，否则拒答。

实测（120 条可答 + 10 条不可答）：

| 指标 | Hash 基线 | 本地 BGE |
|---|---:|---:|
| 可答问题误拒率 | 0.000 | 0.000 |
| 不可答问题拒答率 | 1.000 | 1.000 |
| 抽取式回答的平均引用支撑度 | 0.993 | 0.990 |
| 被拒绝回答（可答集） | 0 / 120 | 0 / 120 |

口径说明：

- **Recall@5**：top-5 里只要有一个 chunk 与标注同 `doc_id` 即算命中；**MRR@10**：第一个命中的倒数排名。
- **拒答阈值**：对每路原始分（已归一化到 0–1）取最大值，低于 `0.15` 时拒答；不是用 RRF 融合分判阈值。
- **实体门禁**：从问句句首抽主体名（如「星海量子 2024 年营业收入」→ `星海量子`），必须出现在引用片段里，否则拒答；抽不出主体名时不做门禁。
- **引用支撑度**：答案 token 与引用片段 token 的交集 / 答案 token 数（中文按单字 + 二元组分词），是词级近似，不是语义级评审。

## 已知局限

- 语料是 **78 篇**（36 篇东方财富真实新闻 + 合成/样例干扰项），评测集 **120 条可答 + 10 条不可答**，问答由脚本自动生成、标注到**文档级**，不是人工标注；它能验证检索链路与拒答链路，但不能代替人工评测。正式版需要做 40–60 条人工标注。
- 向量检索是暴力余弦，chunk 上万后要换 ANN。
- 忠实度是词级覆盖近似，不是语义级评审。
- BGE 是检索侧模型，不是生成侧 LLM；仓库没有接入生成模型做端到端答案评测。

## 开发方式

本仓库按「AI 辅助开发 + 机械门禁」的方式推进：改动前先检索复用点，改完跑测试与静态分析再提交，提交信息里写清验证证据。
