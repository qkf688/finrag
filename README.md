# FinRAG

金融知识库 RAG 检索层与评测 —— 独立项目，目标是把「LLM + 检索」做出**可复现、可量化**的证据。

对应 JD 要求（`AI 全栈开发工程师`）：req-005 搭建与优化金融 RAG 知识库与检索增强生成系统（must_have）。

## 为什么做这个

- 这类岗位的 JD 写的是「搭建和优化」，落点就是**评测数字**：检索召回率、答案忠实度、延迟。没有数字就只是堆功能。
- 独立仓库叙事更清楚：不挂在别的项目下面，README 一眼能看懂「做了什么、怎么测的、结果如何」。
- 全流程离线可复现：默认用哈希基线做检索评测，模型可替换；没有 GPU、没有 API key 也能把评测表跑出来。

## 架构

```
corpus/*.md ──split.py──> chunk(doc_id, section, text)
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        BM25（纯 Python）              embed.py（Hash / 本地模型）
              │                               │
              └──────── retrieve.py ─────────┘   serve/测量：BM25 单路｜报告：RRF 对照
                              │
                     answer.py 组装带引用的答案 / 拒答
                              │
                     evaluate.py 出评测表
```

- `src/finrag/split.py`：按标题 + 段落切分，带 overlap。
- `src/finrag/embed.py`：中文按「单字 + 二元组」分词；`HashEmbedding` 是确定性离线基线，`LocalEmbedding` 用本地 bge-small-zh。
- `src/finrag/retrieve.py`：BM25 + 向量索引 + RRF 混合召回；Web 演示与生成侧测量只走 BM25 单路（`hybrid_search` 不传 `vec_scores`），`make report` 的四组对照仍用 RRF。
- `src/finrag/answer.py`：提示词要求「只依据片段回答」，输出 JSON（答案 + 引用）；得分低于阈值直接拒答。
- `src/finrag/evaluate.py`：Recall@K / MRR@K / 引用支撑度 / P50、P95 延迟。

## 复现实验

在仓库根目录设置 `PYTHONPATH=src`（Windows PowerShell：`$env:PYTHONPATH="src"`）：

```bash
python -m ruff check src tests
python -m pytest -q
python -m finrag.cli report --backend hash --out results/report-hash.md
python -m finrag.cli report --backend local --out results/report-local.md
```

`report` 会重新生成上面的表；`local` 需要本机可用的 sentence-transformers 与 bge-small-zh。

## Web 演示

单页查询台，输入问题后返回答案、引用原文和两条检索分数；主体名不在语料中或相关度低于阈值时拒答，并说明是哪种原因。

```bash
make serve-setup   # 装 fastapi / uvicorn / httpx
make serve         # http://127.0.0.1:8000
```

页面是 `src/finrag/web/index.html`，原生 HTML/CSS/JS，零外链、可离线打开；接口为 `POST /api/query` 与 `GET /api/health`，索引按后端在首次请求时构建并缓存。

哈希后端首次请求约 0.6 秒；`bge` 后端首次要加载模型并编码 375 个 chunk，本机实测约 80 秒。2026-11-28 起检索固定为 BM25 单路，`backend` 只决定构建哪个嵌入索引、不再影响排序结果，演示用默认 `hash` 即可。


## 评测表

### 真实语料（东方财富公开财经新闻，2026-11-23 抓取）

- `scripts/fetch_eastmoney_corpus.py`：列表页 → 36 篇正文（保留原文 URL 与抓取日期）；
- `scripts/make_real_eval.py`：从真实正文自动构造 120 条问答，每条标注**生成该问题的那个 chunk**（`relevant_chunk_ids` 精确到 `doc#section#i`）；
- 评测口径：本节的表格由 `experiment.py` 计算，`cli eval` 走 `evaluate.py`，两者都是**精确 chunk_id 一致**才算命中，数值可直接比较（`cli eval` 的向量候选宽度等于 `top_k`，报告路径是 10，故同一后端下 `cli eval` 略低）。拒答评测里实体门禁识别不出主体名时跳过。

`python -m finrag.cli report` 实测（k=5，数值来自 `results/report-hash.md` 与 `results/report-local.md`）：

**HashEmbedding 512 维离线基线**

| 方案 | Recall@5 | MRR@10 | P50 (ms) | P95 (ms) |
|---|---:|---:|---:|---:|
| BM25 | 0.775 | 0.666 | 6.655 | 7.607 |
| 纯向量 | 0.550 | 0.407 | 16.524 | 97.895 |
| 混合召回（RRF） | 0.592 | 0.503 | 131.741 | 188.988 |
| 混合 + 重排 | 0.592 | 0.519 | 139.208 | 192.468 |

**本地 bge-small-zh（query 侧加中文指令前缀）**

| 方案 | Recall@5 | MRR@10 | P50 (ms) | P95 (ms) |
|---|---:|---:|---:|---:|
| BM25 | 0.775 | 0.666 | 38.412 | 47.975 |
| 纯向量 | 0.425 | 0.330 | 157.164 | 208.732 |
| 混合召回（RRF） | 0.517 | 0.431 | 192.018 | 235.518 |
| 混合 + 重排 | 0.508 | 0.429 | 196.957 | 239.081 |

结论（真实语料，不再全是 1.0）：

- **BM25 最强（0.775 / 0.666）**；HashEmbedding 纯向量次之（0.550 / 0.407），本地 bge-small-zh 只有 0.425 / 0.330，低于哈希基线与 BM25，属于负结果，没有继续硬调。
- **混合召回没有超过 BM25**（Hash 0.592 / Local 0.517）。根因见下节「为什么混合召回低于 BM25」。
- **重排只在 Hash 上略正**（0.503 → 0.519），在 Local 上反而略负（0.431 → 0.429）——同一改动在不同 embedding 上结论不同，保留完整对照。
- **延迟**：BM25 在 Hash 下 P50 6.7ms、Local 下 38.4ms；混合路径主要成本是纯 Python 对 375 个 chunk 打分，上规模后要换倒排索引。

#### 为什么混合召回低于 BM25

把 RRF 拆开看，`retrieve.hybrid_search` 融合的两路**长度并不对称**：BM25 那一路是**全库 375 个 chunk** 的完整排名，向量那一路只有 `vec.search(qv, top_n)` 返回的候选（报告路径 `experiment.py` 里 `top_n=10`，`cli eval` 路径则等于 `top_k`）。两路按同一个 `1/(60+rank)` 相加，于是：

- 向量第 1 名得 `1/61 ≈ 0.0164`，而 BM25 第 50 名只得 `1/110 ≈ 0.0091`。一个「向量第 1 + BM25 第 50」的 chunk 合计 `0.0255`，**超过 BM25 单独第 1 名的 `0.0164`**。弱检索器的一条命中就能顶掉强检索器的头名。
- 更普遍的是「地板效应」：向量 top-10 每项至少 `1/70 ≈ 0.0143`，而 BM25 单路第 10 名往后全部低于这个值。10 条向量命中因此被近乎无条件地压到 BM25 的尾巴之上。
- 实测：现状 hybrid top-5 共 600 个位置，其中 **141 个（23.5%）是 BM25 排名 10 之外的 chunk**；逐题比较，120 题里 **25 题变差、3 题变好、92 题持平**。
- 反向验证：只喂 BM25 一路进 RRF（不传向量），recall@5 / MRR@10 与纯 BM25 **完全相同**（0.775 / 0.666），说明 RRF 融合本身不损，问题出在第二路的注入。

改法对照（同一评测集、精确 chunk id 口径，逐项单变量）：

| 变体 | Recall@5 | MRR@10 |
|---|---:|---:|
| BM25 单路（基线） | **0.775** | **0.666** |
| 现状：BM25 全库 + 向量 10，k=60 | 0.592 | 0.503 |
| 向量也取全库（375），k=60 | 0.675 | 0.543 |
| 两路都截断到 10，k=60 | 0.733 | 0.553 |
| 两路都截断到 100，k=60 | 0.675 | 0.543 |
| 现状宽度，k=10 | 0.608 | 0.511 |
| 现状宽度，k=1 | 0.708 | 0.567 |
| 现状宽度，向量权重 0.5 | 0.583 | 0.520 |
| 现状宽度，向量权重 0.3 | 0.658 | 0.544 |

结论：把两路候选宽度对齐（都取 10）能把 0.592 拉回 0.733，是表里最有效的一改；但**没有任何变体超过 BM25 单路的 0.775**。原因是这份评测集的问题由正文句子改写而来、答案就在生成它的那个 chunk 里，查询词几乎都出现在原文里，词面匹配已经是接近最优的信号——向量那一路在这里不是补充信息，只是噪声。因此**对外报告、Web 演示与生成侧测量都用 BM25 单路**（`serve.py` 与 `scripts/measure_gen_quality.py`，2026-11-28 起），不为「混合」而混合；`hybrid_search` 保留给 `make report` 的四组对照。若将来换成语义型问句（改写、跨表述、多跳），需要重新测，那时宽度对齐应当作为第一项必做的修正。

复现：诊断脚本不进仓库（一次性分析），做法是从 `eval/qa.jsonl` 逐题取 BM25 全库分与向量全库分，再按上表各配置自行融合。评测集与语料在仓库内，数字可自行核对。

### 合成语料（早期基线，对照用）

40 篇合成金融文档 + 80 条问答，每个 section 都带唯一公司名：

| 方案 | Recall@5 | MRR@10 |
|---|---:|---:|
| BM25 | 1.000 | 0.721 |
| 纯向量 | 1.000 | 0.760 |
| 混合召回（RRF） | 1.000 | 0.727 |
| 混合 + 重排 | 1.000 | 0.688 |

合成基准太易，Recall 全 1.0；重排在合成集上是负结果（0.727 → 0.688），在真实集上略正（0.503 → 0.519）——同一改动在不同数据上结论相反，这正是要做多组对照的原因。

## 拒答与引用（实体门禁）

金融问答里「同名指标不同公司」靠分数阈值挡不住：问「星海量子 2024 年营业收入」，语料里每家公司都有「2024 年营业收入」这句话，BM25 分数照样很高。所以加了一层实体门禁：从问句开头抽出主体名（`星海量子`），必须出现在引用片段里，否则拒答。

实测（120 条可答 + 10 条不可答）：

| 指标 | Hash 基线 | 本地 BGE |
|---|---:|---:|
| 可答问题误拒率 | 0.000 | 0.000 |
| 不可答问题拒答率 | 1.000 | 1.000 |
| 抽取式回答的平均引用支撑度 | 0.993 | 0.990 |
| 被拒绝回答（可答集） | 0 / 120 | 0 / 120 |

口径说明：

- **Recall@5**：top-5 里只要有一个 chunk 与标注同 `doc_id` 即算命中；**MRR@10**：第一个命中的倒数排名。
- **拒答阈值**：对每路原始分（已归一化到 0–1）取最大值，低于 `0.15` 时拒答；不是用 RRF 融合分判阈值。
- **实体门禁**：从问句句首抽主体名（如「星海量子 2024 年营业收入」→ `星海量子`），必须出现在引用片段里，否则拒答；抽不出主体名时不做门禁。
- **引用支撑度**：答案 token 与引用片段 token 的交集 / 答案 token 数（中文按单字 + 二元组分词），是词级近似，不是语义级评审。

## 生成侧质量（LLM 路径）

上面的表都是检索指标。生成侧另测一次：本地网关跑 `--limit 50` 可答题 + 10 条不可答题（BM25 单路检索、`top_k=5`、`temperature 0.1`，2026-11-28）。

| 指标 | 值 |
|---|---:|
| 检索命中金标 chunk@5 | 0.720（36/50） |
| 模型作答率 | 0.960（48/50） |
| 作答里引用零编造（citations ⊆ 检索片段） | 1.000（48/48） |
| 平均引用支撑度 | 0.896 |
| 检索命中时模型作答率 | 0.972（35/36） |
| 检索未命中时模型拒答率 | 0.071（1/14） |
| 不可答题正确拒答率 | 1.000 |

结论是**生成的瓶颈在检索**：命中时 97% 能答；未命中时模型几乎都作答（14 题只拒 1 题），但那些回答多是题干歧义下从片段里挑出的可追溯枚举，不等于有依据。所以提升端到端表现应先投检索（评测集修正、表格解析），而不是换更大的模型。检索从向量候选切到 BM25 单路后，命中金标 0.560 → 0.720、误拒率 0.260 → 0.040。引用零编造说明来源可追溯，但不等于答案正确。拒答判定在 `temperature 0.1` 下抖动明显，单次数字只当量级参考。

细节、局限与复现方法见 [`docs/gen-quality.md`](docs/gen-quality.md)（`make gen-quality`）。

## 公开基准：FinanceBench 页级检索

自建 120 条问答由脚本从正文句子改写生成、标注到生成该问题的那个 chunk。为了有一个第三方能核对的参照，加了 [FinanceBench](https://github.com/patronus-ai/financebench)（arXiv 2311.11944）的页级检索评测：150 题开源子集、84 份真实 10-K / 10-Q / 8-K / Earnings（12,013 页、43,605 个 chunk），复用仓库自己的 BM25 全库打分。

| 指标 | @1 | @3 | @5 |
|---|---:|---:|---:|
| 页级命中（oracle 文档内排序） | 0.153 | 0.233 | 0.307 |
| 证据覆盖（词元重合 ≥ 0.8） | 0.067 | 0.160 | 0.220 |
| 全库文档命中（参考） | 0.247 | 0.373 | 0.480 |

按题型（page hit@3）：domain-relevant 0.200（50 题）、metrics-generated 0.120（50 题）、novel-generated 0.380（50 题）。数值题要读表格，固定字符窗把表头与数字拆开，是主要短板。

口径与完整说明见 [`docs/financebench.md`](docs/financebench.md)，要点：

- 只测检索，不测生成：金答案多为 `$1577.00` 这类短数值，答案准确率需要生成模型与判定器。
- 页级命中采用 oracle 文档设定（题目自带文档名），是页定位上界；全库 doc hit@5 只有 0.480，跨文档检索是另一道题。
- 公开子集只有 150 / 10,231 题；官方没有公布检索基线，本表不能与论文的 Oracle 85%、长上下文 79% 直接比。
- 不能与上表新闻语料的 Recall@5 0.775 直接比：那是 chunk 级、78 篇语料、问题由正文句子改写生成；这里是页级、84 份真实财报。

复现：`make bench-setup` → `make financebench`，PDF 按需下载，报告写到 `results/financebench.md`。

## 已知局限

- 语料是 **78 篇**（36 篇东方财富真实新闻 + 合成/样例干扰项），评测集 **120 条可答 + 10 条不可答**，问答由脚本把正文句子改写成问句、答案就在原句所在 chunk，不是人工标注；它能验证检索链路与拒答链路，但不能代替人工评测——问题由原文改写而来，词面重合度高，指标偏乐观。正式版需要做 40–60 条人工标注。上一节的 FinanceBench 是公开数据、可被第三方核对，但它只测检索，不能替代人工标注的答案评测。
- 向量检索是暴力余弦，chunk 上万后要换 ANN。
- 忠实度是词级覆盖近似，不是语义级评审。
- 生成侧只测到「引用可追溯 + 支撑度」这一层：没有答案正确率的语义判定（金答案是 `$1577.00` 这类短值或一句话时，需要 LLM judge 或人工判分）。
- 演示页只拦两类问题：相关度低于阈值，以及「主体名 + 年份」句式里主体名不在语料中。自然离题的日常问句（例如「如何做提拉米苏」）抽不出主体名，不会被实体门禁拦住，仍会返回一条财经片段，这是哈希基线的固有局限。

## 开发方式

本仓库按「AI 辅助开发 + 机械门禁」的方式推进：改动前先检索复用点，改完跑测试与静态分析再提交，提交信息里写清验证证据。
