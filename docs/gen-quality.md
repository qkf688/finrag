# 生成侧质量（LLM 路径）

检索评测（Recall / MRR / FinanceBench 页级命中）只说明「正确的片段有没有被捞出来」，不说明「模型拿到片段后答得怎么样」。这一页补上后者：用本地 OpenAI 兼容网关（默认 `trae-cn/deepseek-v4.1-flash`，`temperature 0.1`）跑 50 条可答题 + 10 条不可答题，测量引用遵循率、引用支撑度、答案对金标片段的覆盖，以及拒答行为。

测量日期 2026-11-27，`hash` 后端，`top_k=5`，可答题从 `eval/qa.jsonl`（120 条）等距取 50 条。

## 结果

| 指标 | 值 |
|---|---:|
| 检索命中金标 chunk@5 | 0.560（28/50） |
| 模型作答率 | 0.740（37/50） |
| 作答里引用零编造（citations ⊆ 检索片段） | 1.000（37/37） |
| 平均引用条数 | 1.22 |
| 平均引用支撑度（答案 token 落在引用片段） | 0.880 |
| 答案 token 落在金标 chunk 的比例 | 0.631 |
| 金标 chunk 被答案覆盖的比例 | 0.118 |
| 检索命中时模型作答率 | 0.893（25/28） |
| 检索未命中时模型拒答率 | 0.455（10/22） |
| 不可答题（10 条）正确拒答率 | 1.000 |

## 怎么读这张表

1. **生成的瓶颈在检索，不在模型。** 检索命中金标的 28 题里，模型答了 25 题（0.893）；检索没命中的 22 题里，模型只答了 12 题、拒答 10 题（0.455）。也就是说，模型几乎不会在「片段确实包含答案」时说不出话，而「答不出来」大多是因为检索没给到。要提升端到端表现，先投检索（两路宽度对齐、表格解析），而不是换更大的模型。
2. **引用可追溯，但不等于答案正确。** 37 条作答的 citations 全部是本次检索提供的 chunk id（零编造）——因为提示里已给出 id 列表，模型只需复制。这证明「引用来源可核对」，但不能当准确性证据。
3. **引用支撑度 0.880**：答案的绝大多数词能在它自己引用的片段里找到，属于「有据可查」的下限证据；词级近似，不是语义级评审。
4. **「金标被答案覆盖」只有 0.118，不要当错误率读**：金标是该题来源的整段 chunk（可能上百字），而答案通常只有一句，分母天然大。该值只用于纵向比较，不用于判定对错。
5. **未命中金标仍作答的 12/22 条是需要人工复核的一批**：可能是相邻 chunk 讲同一件事（合理），也可能是拼凑（不可接受）。这是当前最该抽查的部分。
6. **不可答题目 100% 拒答**：离题问句在 LLM 模式下会被「无引用即拒答」的规则挡住，这是相对抽取式路径的明确改进。

## 局限

- 样本 50 + 10 条，`hash` backend，单次运行。
- 问题由正文句子改写生成（答案就在原句所在 chunk），词面重合度高，指标整体偏乐观——与检索评测同一局限。
- **拒答判定在 `temperature 0.1` 下抖动明显**：同一份 25 条子集两次跑出误拒率 0.520 与 0.400，50 条为 0.260。该指标需多次运行取均值才可作为结论，单次数字只当作量级参考。
- 引用支撑度与覆盖度都是词级近似（中文单字 + 二元组），不做语义判定；不含数值正确性、不含跨文档推理。

## 复现

需要本机有 OpenAI 兼容端点（`FINRAG_LLM_BASE_URL` / `FINRAG_LLM_MODEL` / `FINRAG_LLM_API_KEY`，见 README「接生成模型」）。

```
make gen-quality                                   # 默认 50 条可答 + 10 条不可答
python scripts/measure_gen_quality.py --limit 5    # 小样本试跑
```

脚本为 `scripts/measure_gen_quality.py`：`build_index` → 每题 `hybrid_search` 取 top-5 → `build_prompt` → `chat` → `parse_model_json` → `llm_answer`，再以 `citation_support`（引用支撑度）与 token 交集（金标覆盖）统计；明细默认写 `results/gen-quality.json`（`results/` 已在 `.gitignore` 里）。
